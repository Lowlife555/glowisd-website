# Glowisd 版本号规则（VERSIONING）

> **适用范围：所有参与 Glowisd 官网项目的 agent（dsh / Claude Code / opencode / hermes），无例外。**
> 本规则同步自 `进度看板.md` 变更记录与 `action-manual.md` 项目宪法，以此处为准。
> 版本逻辑综合：**雅思训练网站（V 主.次.补丁 SemVer）** + Glowisd 十进制递增规则（用户指定）。

## 铁律

1. **每次需求变更或 bug 修改之后，都必须升版本号**——不允许"改完不升版"。
2. **首个完成的雏形** 命名为 **`V0.1.0`**。
3. 版本格式 **`Va.b.c`**(V 主.次.补丁),每一位都是 **十进制** 逐位递增:
   - `V0.1.0 → V0.1.1 → V0.1.2 → … → V0.1.9 → V0.2.0 → V0.2.1 → …`
   - 个位满 `9` 进位到前一位(`V0.1.9` 下一个是 `V0.2.0`),**不允许跳号、不允许随意改名**。

## 版本位语义（借鉴雅思训练网站）

| 位 | 含义 | 触发条件 |
|----|------|----------|
| **a 主版本** | 重大改版/架构重构 | 技术栈更换、流程重构、数据体系重建 |
| **b 次版本** | 新功能 | 新增页面、新交互、新模块、需求变更 |
| **c 补丁** | Bug 修复 | 修复缺陷、优化体验、文案调整 |

> 判断不清时:**任何变更一律至少升 `c`(补丁)**,即 `Vx.y.z → Vx.y.(z+1)`。

## 必须标注版本号的场景

- 交付物、发布包、构建产物
- `README.md`、CHANGELOG、发布说明
- 演示给客户/展商的版本
- git tag、package.json `version` 字段
- **git commit message 以 `V X.X.X:` 开头**(如 `V0.1.1: 修复询价表单邮箱校验`)

## 流程

1. 完成需求变更或 bug 修复 → 按语义决定升 a/b/c → 计算新版本号
2. 更新 README「版本记录」表 + CHANGELOG(如有)
3. 在 `进度看板.md` 变更记录追加一行(格式:`- 日期 | 版本 X → Y | 原因 | 影响任务`)
4. git commit 以 `V X.X.X:` 开头,并打 git tag `VX.X.X`
5. 若与部署相关,同步更新线上版本

## 示例

| 当前版本 | 变更类型 | 下一个版本 |
|----------|----------|-----------|
| V0.1.0 | Bug 修复 | V0.1.1 |
| V0.1.8 | 文案调整(补丁) | V0.1.9 |
| **V0.1.9** | 新功能(次版本) | **V0.2.0** |
| V0.2.9 | 新增页面(次版本) | V0.3.0 |
| V0.3.0 | 架构重构(主版本) | V1.0.0 |
| V1.9.9 | 重大改版 | V2.0.0 |

## 速记

> 每次改完必升版;十进制逐位进:个位满 9 进十位,十位满 9 进百位。首版永远从 **V0.1.0** 开始。
